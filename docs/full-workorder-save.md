# Сохранение бланка и карточек клиентов

Бланк больше не создаёт и не редактирует записи справочника клиентов, контактов и велосипедов.
Передача старого поля `details` при сохранении бланка возвращает HTTP 400.

## Справочник

- `GET /api/clients?query=...` — список или поиск. Ответ: `exact`, `similar`, `autoSelect`.
  Автоматический выбор разрешён только при единственном точном совпадении полного нормализованного телефона.
  Совпадения телефона без первых трёх цифр попадают в `similar` и требуют ручного выбора.
- `GET /api/clients/{id}` — актуальная карточка, контакты и велосипеды.
- `POST /api/clients` — создание самостоятельной карточки.
- `PUT /api/clients/{id}` — изменение с обязательной текущей `version`.
- `POST /api/clients/{id}/bicycles` — отдельное создание велосипеда.
- `PUT /api/clients/{id}/bicycles/{bicycleId}` — изменение с версией велосипеда.
- `GET /api/contact-types` — типы контактов.

Тип `PERSON` требует имя, фамилию или хотя бы один контакт. `ORGANIZATION` требует
`organizationName`; `representative` — необязательный текст. Тип сохранённой карточки изменить нельзя.
Контакты передаются в `contacts`: `id`, `typeId`, `value`, `label`. Новый контакт имеет `id: null`.
Операции удаления и передачи велосипеда другому владельцу не предусмотрены.

Совпавшие контакты другого клиента возвращают 409 с `code: DUPLICATE_CONTACT`.
После явного подтверждения можно повторить запрос с `allowDuplicateContacts: true`.
Устаревшее редактирование возвращает 409 (`STALE_CARD`); ввод в интерфейсе сохраняется.

## Снимок бланка

`POST /api/work-orders/client-selection` принимает `clientId`, необязательные `bicycleId`,
`contactId`. Возвращает предварительный `snapshot`, `expectedClientVersion`,
`expectedBicycleVersion`, ничего не записывая в бланк.

Сохранение через `POST /api/work-orders` или `PUT /api/work-orders/{number}` передаёт:

```json
{
  "clientId": 1,
  "clientBicycleId": 2,
  "clientContactId": 3,
  "snapshotAction": "REFRESH",
  "expectedClientVersion": 0,
  "expectedBicycleVersion": 0,
  "blankNumber": "00001",
  "createdAt": "2026-11-07T10:00:00Z",
  "reportedIssue": "Не работают тормоза",
  "clientComment": "Комментарий к заказу",
  "internalComment": "Для себя",
  "services": [],
  "products": [
    {"productId": 5, "discountId": 7, "quantity": 2}
  ],
  "customerParts": [
    {"name": "Вилка", "brand": "SR Suntour", "quantity": 1,
     "conditionOnReceipt": "Царапины на ноге", "reportedIssue": "Проверить люфт"}
  ],
  "statusCode": "NEW"
}
```

Создание и изменение выбранных ID формируют новый снимок. `KEEP` при неизменных ID
сохраняет прежний снимок независимо от изменений справочника. `REFRESH` явно обновляет его
при сохранении бланка. Для нового снимка обязательны актуальные версии клиента и велосипеда;
устаревшая версия клиента возвращает 409; версия велосипеда проверяется только при его выборе.
Заказ может содержать велосипед, несколько деталей клиента или велосипед вместе с деталями.
Если велосипед не выбран, нужно передать хотя бы одну деталь клиента. Принадлежность велосипеда
и контакта проверяется сервером.

Ответ разделяет `snapshot` (сохранённые данные бланка) и `client` (актуальный справочник).
`products` — товары мастерской с ценой, скидкой и данными товара на момент заказа.
`customerParts` — детали клиента, принятые вместе с бланком; это не продажи мастерской.
Trello получает имя, представителя, контакт, велосипед (если есть), услуги, товары,
детали клиента и комментарии из заказа.
Доски, колонки и метки читаются через сервер из Trello.

## Применение

Серверный `schema.sql` создаёт каталог товаров, историю их цен и строки товаров/деталей в бланке,
добавляет аудит и снимает обязательность ссылки на велосипед. Старые строки заказов сохраняются.
